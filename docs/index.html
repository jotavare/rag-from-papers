rag-from-papers · how it works

Inside rag-from-papers

A RAG app answers a question in two moves: it finds the right passages in your documents, then asks a language model to answer using only those passages. I made this page to explain each stage of my project using its real numbers: 7 AI papers, 398 chunks, 14 test questions.

Indexing The embedding model Chroma Retrieval Generation Measuring it

Numbers on this page are from my baseline run in November 2026. For setup, usage and the latest results, see the README.

Indexing is like building a library's card catalogue: done once. Retrieval and generation happen each time you run python -m rag.ask "…".

Stage 1 · RAG From Scratch, Part 2

Indexing: turn papers into searchable vectors

A language model can't read 7 full papers for every question, and keyword search misses answers phrased differently. So the papers are cut into small pieces, and each piece gets a list of numbers that captures its meaning.

1. Loadpypdf pulls text out of each PDF, page by page, stopping at the References heading.
2. ChunkEach page is cut into 1,000-character windows that overlap by 200.
3. Embedall-MiniLM-L6-v2 turns every chunk into 384 numbers.About the model ↓
4. StoreVectors, text and page numbers go into a local Chroma database.About Chroma ↓

Try chunking

Why overlap? If a sentence is cut at a chunk boundary, the overlap makes sure it still appears whole in the next chunk. Drag the sliders. The demo uses small numbers so you can see the effect.

What went wrong in my first run

The first run produced 796 chunks, and half were bibliography pages. Reference lists are packed with words like "retrieval" and "generation", so they looked very similar to questions while containing no answers. Three of the top five results for the first test question were citation lists. I fixed it by stopping at each paper's "References" heading.

Stage 1 · under the hood

The embedding model: all-MiniLM-L6-v2

An embedding model reads a piece of text and outputs a fixed list of numbers. Texts with similar meaning get similar lists, even when they share no words. I chose the standard starter model: small, free, runs on a laptop CPU, and good enough to learn with.

What the name means

all-MiniLM-L6-v2
allTrained on a broad mix of datasets: over a billion sentence pairs.
MiniLMA compact model distilled from a larger one.
L6Only 6 transformer layers, which is why it's fast.
v2Second version of the model.
output
384 numbers per chunk
download
about 90 MB; all 398 chunks embed in seconds on CPU
max input
256 tokens; anything after that is silently ignored
released
2021; newer models of the same size retrieve better
A limit that affects this project

The model reads at most 256 tokens. A 1,000-character chunk of English is roughly 200 to 250 tokens, and dense text with formulas or numbers can run longer. When a chunk goes over, its ending is dropped before embedding, so a fact near the end of a chunk may never be searchable.

0 ~225 tokens 256 limit 400

Stage 1 · under the hood

Chroma: the vector database

A regular database finds rows by exact match, like WHERE paper = 'bert'. A vector database finds rows by similarity: "which stored vectors are closest to this one?" That's the question retrieval needs answered.

What Chroma stores for each chunk

id
rag-survey-p1-c0
embedding
[0.021, -0.087, 0.044, … ]
384 numbers
document
Retrieval-Augmented Generation for Large Language Models: A Survey …
metadata
source: rag-survey
page: 1

The embedding is what gets searched. The document text is what the LLM later reads. The metadata becomes the citation. The numbers in the embedding above are shortened placeholders.

HNSW index
A graph linking each vector to its near neighbours. A search hops through the graph toward the closest region instead of comparing against every vector.
hnsw:space
Set to cosine in rag/indexing.py: closeness is measured by the angle between vectors, the usual choice for text.
data/chroma_db/
Chroma runs inside the Python script, with no separate server, and saves everything to this folder. It isn't committed to Git.

Is a vector database needed at this size?

Not strictly. With 398 chunks, comparing the question against every vector in plain Python takes milliseconds. Chroma becomes worth it as the collection grows into hundreds of thousands of chunks, and it saves writing storage code. Alternatives you'll see in tutorials:

OptionWhat it is
ChromaCurrent choice. Embedded in Python, saves to a folder.
FAISSA search library from Meta. Very fast, but doesn't store text or metadata for you.
pgvectorAdds vector search to PostgreSQL.
Qdrant, Weaviate, PineconeVector databases run as servers or cloud services, for production.

    Stage 3 · RAG From Scratch, Part 4

    Generation: answer from the sources, with citations

    The retrieved chunks are numbered and pasted into the prompt. The model is told to use only those sources and to cite them, so every claim can be checked against a page.

    What the model receives

    This is the prompt rag/generation.py builds for my test question.

    System promptYou answer questions about AI research papers. Use ONLY the numbered sources provided. Cite them like [1], [2]. If the sources don't contain the answer, say you don't know.
    Sources (from retrieval)[1] (rag-survey, page 1) Retrieval-Augmented Generation for Large Language Models: A Survey … [2] (rag-survey, page 11) … [3] … [4] … [5] …
    QuestionQuestion: What problem does retrieval-augmented generation solve?

    What came back (Claude, via subscription)

    The survey names three weaknesses of LLMs that RAG targets: hallucination, outdated knowledge, and reasoning that can't be traced [1].

    RAG addresses them by pulling in knowledge from external databases. That makes answers more accurate and credible on knowledge-heavy tasks, and lets knowledge be updated or specialised without retraining [1].

    Shortened. The local Llama 3.2 3B model gave the same three points with the same citation, in about 70 seconds on CPU.

    Swappable models: LLM_BACKEND

    ollamaLocal Llama 3.2 3BFree and offline. Slower and less polished.
    claude-codeClaude via subscriptionBest answers. Counts against the plan's usage limits.
    claudeClaude via API keySame quality, billed per token.

    Retrieval returned the same five chunks for every backend; only the writing changed. That separation is why RAG lets you swap models freely.

    Why "use only the sources" matters

    Without that instruction the model may mix in what it remembers from training, and you can no longer tell which claims come from your documents. With it, a wrong or missing answer usually points back to a retrieval problem, which you can see and fix.

    Measuring it · eval/run_eval.py

    Is it actually working?

    Trying one question tells you little. The evaluation set asks 14 questions with known answers: 13 answerable from a specific paper, plus one off-topic question the app should refuse. Every change to chunking, the embedding model or retrieval can then be scored the same way.

    13/13Right paper in the top 5 (hit@5)
    0.89MRR: 1.0 would mean the right paper always ranks first
    12/14Answers containing the expected facts (Claude)
    What the two failures show

    Both asked about the original RAG paper (Lewis et al.): its two model variants, and which retriever it uses. The paper was retrieved, ranking 4th and 3rd, but not the passage that holds the answer. Claude replied that the sources don't say, instead of guessing. So the grounding instruction works, and the weak spot is retrieval precision: finding the right paper isn't enough, the right chunk has to be found too.

    Run it yourself

    python -m eval.run_eval             # retrieval only: free, a few seconds
python -m eval.run_eval --answers   # also generate and check answers
