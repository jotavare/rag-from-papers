rag-from-papers · how it works

Inside rag-from-papers

A RAG app answers a question by first finding the right passages in your documents, then asking a language model to answer using only those passages. This page walks through the three stages using the real numbers from this project: 7 AI papers, 398 chunks, one question.

Stage 1 · Indexing indexing.py

Papers → chunks → vectors → database

runs once, ahead of time
Stage 2 · Retrieval retrieval.py

Question → vector → 5 closest chunks

runs on every question
Stage 3 · Generation generation.py

Chunks + question → LLM → cited answer

runs on every question

Indexing is the library's card catalogue, built once. Retrieval and generation happen each time you run python ask.py "…".

Stage 1 · RAG From Scratch, Part 2

Indexing: turn papers into searchable vectors

A language model can't read 7 full papers for every question, and plain keyword search misses answers phrased differently. So the papers are cut into small pieces and each piece gets a numeric "meaning fingerprint".

1. Loadpypdf pulls text out of each PDF, page by page.
2. ChunkEach page is cut into 1,000-character windows that overlap by 200.
3. Embedall-MiniLM-L6-v2 turns every chunk into 384 numbers.
4. StoreChunks, vectors and page numbers go into a local Chroma database.

Why overlap? If a sentence is cut at a chunk boundary, the overlap makes sure it still appears whole in the next chunk. Drag the sliders; this demo uses small numbers so you can see it.

What went wrong in this project

The first run produced 796 chunks, and half were bibliography pages. Reference lists are packed with words like "retrieval" and "generation", so they looked very similar to questions while containing no answers. Three of the top five results for the first test question were citation lists. The fix: stop reading each paper at its "References" heading.

Stage 2 · RAG From Scratch, Part 3

Retrieval: find the chunks closest in meaning

The question is embedded with the same model, so it lands in the same space as the chunks. Chunks about similar ideas sit close together. Retrieval returns the 5 nearest ones.

    Stage 3 · RAG From Scratch, Part 4

    Generation: answer from the sources, with citations

    The retrieved chunks are numbered and pasted into the prompt. The model is told to use only those sources and to cite them, so every claim can be checked against a page.

    What the model receives

    System promptYou answer questions about AI research papers. Use ONLY the numbered sources provided. Cite them like [1], [2]. If the sources don't contain the answer, say you don't know.
    Sources (from retrieval)[1] (rag-survey, page 1) Retrieval-Augmented Generation for Large Language Models: A Survey … [2] (rag-survey, page 11) … [3] … [4] … [5] …
    QuestionQuestion: What problem does retrieval-augmented generation solve?

    What came back (Claude, via subscription)

    The survey names three weaknesses of LLMs that RAG targets: hallucination, outdated knowledge, and reasoning that can't be traced [1].

    RAG addresses them by pulling in knowledge from external databases. That makes answers more accurate and credible on knowledge-heavy tasks, and lets the knowledge be updated or specialised without retraining [1].

    Shortened. The local Llama 3.2 3B model gave the same three points with the same citation, in about 70 seconds on CPU.

    Retrieval returned the same five chunks for every backend. Only the writing changed, which is why RAG lets you swap models freely.

    Why "use only the sources" matters

    Without that instruction the model may mix in what it remembers from training, and you can no longer tell which claims come from your documents. With it, a wrong answer usually points back to a retrieval problem, which you can see and fix.
